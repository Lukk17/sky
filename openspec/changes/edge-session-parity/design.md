# Design

## Context

See proposal.md Why. The frontend contract is fixed by `sky-gateway` (`SessionController`, `SecurityConfig` `!local` chain, `OriginCheckWebFilter`) and the Angular `sky-auth.service` (`apiBaseUrl + /oauth2/authorization/keycloak`, `/logout`, `/api/session` with `csrfToken`). The cluster edge today: oauth2-proxy v7.4.0 (`keycloak-oidc`, `upstream: file:///dev/null`, `setAuthorizationHeader/passAuthorizationHeader/passAccessToken/passUserHeaders true`, `cookie-csrf-per-request=true`, `cookie-csrf-expire=15m` hardcoded in the deployment template) fronted by one ingress serving only `/oauth2(/|$)(.*)`; service ingresses carry per-path `auth-url` / `auth-signin` for owner and documentation paths. Prior change `gateway-bff-session-auth` fixed the single-session-owner rule: exactly one owner per environment, which in Kubernetes can only be oauth2-proxy since `sky-gateway` ships no Helm chart.

## Goals / Non-Goals

**Goals:** map every element of the gateway contract onto nginx-ingress plus oauth2-proxy with config only; record the CSRF decision, the TokenRelay-equivalence confirmation, and the frontend-per-environment story; define k3d verification.

**Non-Goals:** any service interior change; any `sky-gateway` code change; changing the OIDC provider, realm, or audience; a second session layer in the cluster; frontend branching per edge.

## Decisions

- **Session endpoint via a dedicated session ingress, not a service route.** nginx cannot synthesize JSON, so `GET /api/session` needs an upstream that can. Options: (a) a tiny session-responder sidecar next to oauth2-proxy answering `{email}` from `X-Auth-Request-Email` / `X-Auth-Request-User` headers behind `auth-url`; (b) routing `/api/session` to an existing service with a new controller. (b) violates service-untouched, so (a): a minimal internal responder (same chart or sidecar) whose ingress carries `auth-url` pointing at oauth2-proxy `/oauth2/auth` plus `auth-signin` to the login path; anonymous callers get 401 with empty body via `auth-url` behavior, authenticated ones get email plus a CSRF token minted by the responder and bound to the oauth2-proxy session. Alternatives rejected: exposing oauth2-proxy `/oauth2/userinfo` directly (wrong shape, leaks claims, wrong path), adding the endpoint to a service (breaks the untouched rule).
- **Login path `/oauth2/authorization/keycloak` as an ingress-level alias to oauth2-proxy `/oauth2/start`.** oauth2-proxy natively serves `/oauth2/start` (login), `/oauth2/callback`, `/oauth2/sign_out`, `/oauth2/userinfo`, `/oauth2/auth` (auth-url probe); it has no `/oauth2/authorization/keycloak` route, and that prefix already routes to oauth2-proxy. So a cluster ingress rule (rewrite or `configuration-snippet` location) maps the gateway-identical login path to `/oauth2/start` with `rd` return-to-frontend-origin preserved. Post-login landing is set via oauth2-proxy `--redirect-url` per overlay (already parameterized) plus `--set-xauthrequest` passthrough. Rejected: teaching the frontend a second login path (breaks zero-difference), running Spring's authorization endpoint in the cluster (that would be a second session owner).
- **Logout `POST /logout` mapped to oauth2-proxy `/oauth2/sign_out`.** Same alias technique: ingress rewrite from `/logout` (POST) to the oauth2-proxy sign-out endpoint, with `post-logout-redirect-uri` back to the frontend origin and Keycloak end-session so SSO ends too. Gateway uses OIDC client-initiated logout; the cluster equivalent is oauth2-proxy sign-out chained to the Keycloak `end_session_endpoint`. Must verify POST (not only GET) survives the rewrite, since the frontend posts.
- **Public routes by omission of auth annotations.** Anonymous `GET /api/v1/offers/**` and `POST /api/v1/search` ingress paths carry no `auth-url`/`auth-signin`; the offer chart already splits public vs owner ingresses for exactly this reason, so extend that pattern and audit every `/api/**` ingress so no other path accidentally drops its auth annotation. Bearer passthrough needs no new flag: `setAuthorizationHeader` and `passAuthorizationHeader` are already `true` in `values.yaml`; verification must prove a caller-supplied Bearer value is forwarded verbatim and still validated service-side (services ignore unknown headers, so CSRF headers pass through harmlessly).
- **CSRF: mechanism-per-edge, identical frontend contract, not service validation.** Compose edge (sky-gateway): session token plus `OriginCheckWebFilter` Origin check. Kubernetes edge: `SameSite=Strict` session cookies (`args.cookieSamesite=strict` in `oauth2-proxy/values.yaml`, wired as `--cookie-samesite` in the deployment template; verified `SameSite=Strict` on `_oauth2_proxy` and `_oauth2_proxy_csrf_*` responses and a green login-to-logout lifecycle on k3d, since the Keycloak callback is same-site with the cookie) plus oauth2-proxy per-request cookie-CSRF (`cookie-csrf-per-request=true`, 15m expiry) as the token layer. Services ignore unknown headers and stay untouched, so they cannot be the CSRF layer on either edge. The nginx `configuration-snippet` Origin/Referer check stays recorded-but-unapplied: the ingress-nginx admission webhook rejects snippets, so until controller policy changes the k8s backstop against cross-site cookie sending is the browser withholding Strict cookies, not an edge rejection. The `/api/session` responder returns the per-session token the frontend stores in memory and sends as `X-XSRF-TOKEN` on both edges. Rejected: disabling CSRF because services ignore the header (leaves cookie-authenticated mutations unprotected), pushing CSRF into services (violates untouched rule), `SameSite=Lax` (unneeded: Strict verified not to break the same-site callback login flow).
- **Frontend: zero differences, origin-only configuration.** Same paths, same `X-XSRF-TOKEN` header, same login/logout flow; only `apiBaseUrl` / app origin differs per environment (existing `environment.*` files). If the session-responder or alias mapping forces any shape difference (e.g. token field name), the decision is to change the cluster side to match, not the frontend. Rejected: per-edge frontend branching.

## Risks / Trade-offs

- [Risk] `/oauth2/authorization/keycloak` collides with the oauth2-proxy ingress prefix semantics (`/oauth2(/|$)(.*)` already routes everything there, but upstream has no such path) → Mitigation: alias/rewrite ingress tested first in k3d before touching overlays.
- [Risk] `auth-url` subrequest behavior on anonymous `/api/session` returns 202/401 with oauth2-proxy HTML rather than empty-body 401 → Mitigation: `auth-url` + `auth-signin` + `custom-http-errors` or snippet tuned so API paths return empty 401; verified by curl in tasks.
- [Risk] POST-to-GET downgrade or method loss on the `/logout` rewrite → Mitigation: explicit method-preserving rewrite, verified with a POST logout lifecycle test.
- [Risk] nginx regex-location precedence across the host (all `use-regex` paths compile as regex, sorted by length) → Mitigation: keep new paths disjoint (`/api/session`, `/logout`, login alias) and verify no shadowing of service paths.
- [Risk] `cookieSecure: false` in `values-local.yaml` vs `true` in prod diverging session behavior → Mitigation: keep the split (HTTP locally, HTTPS in prod) but verify the lifecycle on both overlays.

## Migration Plan

Config-only rollout per environment: render and diff Helm templates, apply to k3d, run Bruno k8s env plus login-to-logout lifecycle, then promote overlays (local overlay first, prod second). Rollback is the previous chart values plus previous ingress manifests; services and frontend need no rollback because neither changes.

## Open Questions

- None that change specs or approach. The exact nginx snippet form (rewrite vs configuration-snippet location) and the session-responder implementation language are left to implementation, bounded by the decisions above.
