# architecture Specification

## Purpose
Holds the four hexagonal services to one package layout and one dependency direction, with the parts a build can check asserted by each service's own ArchUnit test rather than by review, so an adapter cannot quietly reach past a port into a domain service.

## Requirements

### Requirement: Hexagonal layer separation is enforced by ArchUnit
Each of the four hexagonal services (sky-booking, sky-offer, sky-message, sky-notify) MUST carry an ArchUnit test in its own test source, and every guarantee stated here MUST name the thing that enforces it, which is either a rule in those tests or the Gradle module graph. A guarantee that nothing enforces MUST NOT be written as though a test enforced it. The dependency direction is that `adapters` MAY depend on `domain` and on `sky-common`, that `config` MAY depend on both `adapters` and `domain` because it is the composition root that wires one to the other, and that `domain` MUST depend only on the packages the allow list below names. The `config` permission carries no rule and MUST NOT be described as enforced, because a permission has nothing for a rule to fail on.

The domain of a service that stores something MUST be permitted exactly these and nothing else: its own `domain` packages, `com.lukk.sky.common`, `java`, `jakarta.persistence`, `jakarta.validation`, `lombok`, `org.slf4j`, the single type `org.hibernate.Hibernate` for the entity identity contract, `org.springframework.context.annotation`, `org.springframework.data.domain`, `org.springframework.data.jpa.repository`, `org.springframework.stereotype`, `org.springframework.transaction.annotation`, and `org.springframework.util`. An earlier wording said the domain may depend only on itself, on `sky-common` and on `java`. That was never true of any service and it contradicted the requirement on the canonical package layout in this same specification, which places every `@Entity` in `domain.model` and every repository interface in `domain.ports.outbound`. This project has deliberately chosen one class to serve as both the domain model and the persistence entity, so the persistence and validation entries are design rather than accident, and the cost of that choice is that the domain is not framework independent. Adopting separate persistence entities with a mapper on each side would remove those entries and is a decision in its own right, not a side effect of writing a rule. sky-notify MUST carry a shorter allow list holding no persistence, validation or Spring Data entry, because it relays events and stores nothing.

Three entries in that allow list are recorded as deviations to be resolved rather than as design, and no new code MAY rely on any of them. `com.lukk.sky.<service>.adapters.dto` is permitted because the domain handles the wire DTO directly instead of a command or result type of its own, in `domain.service`, in the driving port under `domain.ports.inbound` that returns it, and in the driven notification port under `domain.ports.outbound` that takes it. That last one is where the deviation is paid for deliberately: the notification port names the DTO so the adapter keeps the serialisation, which is the alternative to putting `tools.jackson.databind` into `domain.service`, and the sentence below forbids new code from doing that. `tools.jackson.databind` is permitted in sky-booking and sky-offer because the event source service serialises that DTO into an event payload inside the domain, where serialisation is an adapter concern. The one class annotated `@RestControllerAdvice`, which lives under `domain.exception` in sky-booking, sky-offer and sky-message, is a driving adapter sitting in the domain, and it MUST be carved out by its annotation rather than by its package so that exactly one class is exempt. That carve-out MUST additionally permit `org.springframework.http`, the package `org.springframework.web` itself for `ErrorResponse`, and `org.springframework.web.bind.annotation`, and it MUST NOT permit `org.springframework.web` and everything beneath it, because that would admit an HTTP client into the domain and falsify the scenario below.

No class in a service MAY depend on a class belonging to another service. The primary guarantee is the Gradle module graph rather than a test: each service's `build.gradle.kts` declares `implementation(project(":sky-common"))` and no other project dependency, so another service's classes are not on the compile classpath and the import does not compile. Each service MUST also carry an ArchUnit rule asserting it, matching any `com.lukk.sky` package other than the service's own root and `com.lukk.sky.common`, so that a fifth module needs no edit. That rule is a second line and MUST NOT be credited with the whole guarantee, because it can only fire on a tree whose build file already permits the import, which makes the build file the artefact a reviewer has to watch.

No class under `adapters.inbound` MAY depend on a Spring Data repository or on an interface whose simple name ends in `Repository`. sky-booking, sky-offer and sky-message MUST each carry that rule, and sky-notify MUST NOT, because it holds no persistence and a rule matching nothing there would read as enforcement while checking nothing. This rule is needed because a repository interface lives in `domain.ports.outbound` and is therefore a port, so the older rule forbidding an adapter from reaching `domain.service` never covered it and a controller could inject a repository with nothing objecting.

No class under `adapters.inbound` MAY depend on a class under `domain.ports.outbound`. A repository is one driven port among several, so the rule above closes one member of the family and leaves the rest open, which is how a controller was able to inject a notification port and publish its own Kafka event on the side. sky-booking and sky-offer MUST each carry this rule, because each had a controller doing exactly that until it was moved. sky-notify MUST NOT, because it has no `domain.ports.outbound` package at all and keeps one flat `domain.ports`, so the selector would match nothing and the rule would read as enforcement while checking nothing. sky-message does not carry it yet and this is recorded as a gap rather than written as enforced: it holds both packages so the rule would bite there, and the only interface its `domain.ports.outbound` holds today is `MessageRepository`, which the repository rule already covers, so what is missing is a second line rather than a guard on an open hole.

Where a driven port is called from MUST NOT be read as a layering detail alone, because it decides when the side effect happens. An inbound adapter calling a driven port runs that call outside every boundary the domain service establishes, so the effect is neither ordered against the domain's own steps nor covered by the transaction the service opens. Moving such a call inward MUST be recorded in the module guide of the service it moves in, naming what the relationship between the effect and the commit was before and what it is afterwards, because that relationship is the substance of the move rather than a side effect of it.

Every rule named here MUST have been observed failing on a deliberate violation before it is relied on, because an ArchUnit rule whose selector matches nothing passes and reads like enforcement. A rule that cannot be made to fail MUST be reported as doing nothing rather than kept.

#### Scenario: A controller bypasses the service layer
- **WHEN** a developer adds a field injecting a `*Repository` directly into a controller in sky-booking, sky-offer or sky-message, skipping the service layer
- **THEN** that service's ArchUnit test fails the build, naming the field and the constructor parameter that carry the repository type

#### Scenario: A domain class imports a Spring web type
- **WHEN** a developer adds `import org.springframework.web.client.RestClient` to a class in `domain.*`, including the `@RestControllerAdvice` under `domain.exception`
- **THEN** the ArchUnit allow list rule fails the build, because no domain class and no carve-out admits the Spring web client packages

#### Scenario: A service reaches into another service
- **WHEN** a developer adds a second `implementation(project(...))` entry to a service's `build.gradle.kts` and imports a class from that other service
- **THEN** the importing service's ArchUnit test fails the build, naming the foreign class, and the build file edit that made the import compile is visible in the same change

#### Scenario: The domain gains a framework the specification has not admitted
- **WHEN** a developer adds a dependency on a package outside the allow list to any class under `domain`, in any of the four services
- **THEN** that service's ArchUnit test fails the build, and admitting the package requires changing this requirement first rather than adding an exclusion to the test

#### Scenario: A controller publishes its own event through a driven port
- **WHEN** a developer injects an outbound notification port into a controller in sky-booking or sky-offer and publishes from the inbound adapter
- **THEN** that service's ArchUnit test fails the build, naming the field and the constructor parameter that carry the port type, and the publication belongs in the domain service that decides whether the request succeeded at all

### Requirement: Canonical package layout per service
Each of the four hexagonal services (sky-booking, sky-offer, sky-message, sky-notify) MUST organise its source under one root package named for the service, holding `adapters`, `domain` and `config` and nothing else at that level. Within `adapters`, wire types MUST live in `adapters.dto`, a driving adapter MUST live under `adapters.inbound` and a driven adapter under `adapters.outbound`, and each driven adapter MUST sit in a subpackage named for what it adapts, as `adapters.outbound.persistence`, `adapters.outbound.rest`, `adapters.outbound.notification`, `adapters.outbound.storage` and `adapters.outbound.websocket` do. There MUST NOT be a package named `adapters.api` or `adapters.persistence` directly under `adapters`, because an adapter's direction is the first thing a reader needs from its package name and a technology name at that level hides it. Within `domain`, entities MUST live in `domain.model`, domain exceptions in `domain.exception`, port interfaces under `domain.ports` split into `domain.ports.inbound` for the ports a controller calls and `domain.ports.outbound` for the ports an adapter implements, and the implementations of those ports in `domain.service`. Spring wiring MUST live in `config`, with bound property records in `config.propertyBind` and Kafka wiring in `config.kafka`. Three of these locations MUST be enforced by an ArchUnit rule in the service's own test source rather than left to review: a class annotated `@RestController` or `@Controller` resides in `adapters.inbound.api`, a class annotated `@Entity` resides in `domain.model`, and a repository interface resides in `domain.ports.outbound`. sky-notify MUST additionally carry two rules over the name of a driven adapter subpackage, because the rule that covers its one driven adapter gated the whole of `adapters.outbound` without looking at the name, which is how the name it carried until now was able to drift. The first rule places the class that depends on `SimpMessagingTemplate` in `adapters.outbound.websocket` rather than anywhere under `adapters.outbound`. The second forbids any package under `adapters` from being named `service`, `impl` or `util`, and it MUST be read as an approximation rather than as enforcement of the whole sentence above, because no rule can judge whether a name describes what it adapts, so it closes the family of names that describe nothing instead. On naming, a REST controller MUST end in `Controller`, and the single implementation of an interface MUST take that interface's name with the suffix `Primary`, which holds in `adapters.outbound` exactly as it does in `domain.service`. A port interface MUST NOT carry a `Port` suffix, because its package already says it is a port and it is named for what it does instead.

A package named above MAY be absent from a service that has no such concern, and the absence MUST follow from the service's shape rather than from a different layout. Four such absences hold today and each is accounted for. sky-message has no `adapters.outbound`, because it has no driven adapter left, and no `config.kafka`, because it publishes no events. sky-notify has neither `domain.model` nor `domain.exception`, because it relays events and stores nothing. sky-notify also keeps one flat `domain.ports` package instead of the inbound and outbound split and carries no `adapters.inbound.api`, because it exposes no REST surface and holds a single port, and its own ArchUnit rules gate `adapters.inbound` and `adapters.outbound` without naming an `api` subpackage. A new service MUST follow the split layout rather than sky-notify's, and sky-notify's shape MUST NOT be read as a second sanctioned layout.

`sky-gateway` and `sky-common` are outside this requirement. `sky-gateway` is an edge proxy whose routing table is configuration rather than code, holding no domain model and carrying no ArchUnit test, so imposing the layout on it would create empty packages. `sky-common` is a shared library organised by the concern each package serves rather than by the hexagon.

#### Scenario: New contributor navigating across services
- **WHEN** a contributor finds the booking controller at `sky-booking/src/main/java/com/lukk/sky/booking/adapters/inbound/api/BookingController.java`
- **THEN** the equivalent controller in another service sits at the same relative path, as sky-offer's `OfferApiController` and sky-message's `MessageController` both do under `adapters/inbound/api`

#### Scenario: A controller placed outside the inbound adapter package fails the build
- **WHEN** a developer adds a class annotated `@RestController` anywhere outside `adapters.inbound.api` in sky-booking, sky-offer or sky-message
- **THEN** that service's own ArchUnit test fails the build, because the rule asserts the location rather than documenting it

#### Scenario: Comparing the four services against the layout
- **WHEN** an auditor lists the packages of all four services and checks each one against the layout named here
- **THEN** every package either carries a name this requirement gives or is a subpackage of one of them named for the concern it holds, and the only gaps and deviations are the ones this requirement names, which are sky-message missing `adapters.outbound` and `config.kafka`, sky-notify missing `domain.model`, `domain.exception` and `adapters.inbound.api` while keeping one flat `domain.ports`

#### Scenario: A driven adapter lands in a package named for nothing
- **WHEN** a developer adds a class to sky-notify under a package named `service`, `impl` or `util` anywhere beneath `adapters`, or moves the class depending on `SimpMessagingTemplate` out of `adapters.outbound.websocket`
- **THEN** sky-notify's ArchUnit test fails the build, naming the class and the package it landed in
